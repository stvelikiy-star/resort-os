# MARINA SMART — первичные файлы финансовых корректировок, P0

**Ветка:** Draft поверх #545. **Статус:** проверяем байты, но не утверждаем бухгалтерскую подлинность и не признаём прибыль.

## Архитектура без внешнего хранилища

- `zz125_marina_owner_revenue_evidence_bytes_20261116` добавляет неизменяемую таблицу `owner_revenue_evidence_documents`, где хранится **оригинальный BYTEA** и отдельные реквизиты. SQL-триггер запрещает UPDATE/DELETE. Данные документов входят в штатный PostgreSQL backup/restore; серверы и сервисы на Ubuntu не меняются.
- Один файл — до **2 MiB** (преднамеренный лимит для текущей локальной инфраструктуры), только `application/pdf`, `image/png`, `image/jpeg`. Проверяются сигнатура файла, допустимый размер и реальный SHA-256 от декодированных байтов; одна строка с чужим hash возвращает 409.
- `POST /api/v1/admin/finance/owner/revenue-evidence` — JSON с `id` UUID, `document_reference`, `document_date`, `file_name`, `media_type`, `sha256`, `content_base64`. Все проверки/запись происходят **только для OWNER**. Повтор того же ID и байтов идемпотентен, изменение ID-полезной нагрузки возвращает 409.
- `GET /api/v1/admin/finance/owner/revenue-evidence/{id}` — реквизиты, `GET .../{id}/content` — только OWNER, полный байтовый файл с повторной проверкой SHA, заголовками `no-store` и `attachment`. Путь имени файла формируется из UUID, а не из пользовательской строки.
- `zz125` добавляет `evidenceDocumentId` и FK `(propertyId, evidenceDocumentId)` к каждой новой корректировке в `owner_revenue_correction_events`. Новая операция RECORD без ID документального подтверждения отвергается. Сервис проверяет, что **из своей гостиницы** найдены неизменяемые байты, номер, дата и SHA, прежде чем создавать операцию.
- REVERSAL копирует ID документа исходной корректировки и создаёт **новое событие**. Запрещено редактирование исходных строк.
- Web/Mobile OWNER получают счётчики документов, имеющих серверно подтверждённые байты, и отсутствующих файлов; признанная выручка и прибыль остаются `null`.

## Ограничения проверки

1. Совпадение SHA-256 с сохранёнными байтами подтверждает **целостность файла**, но не юридическую подлинность, полномочия подписанта и не факт оплаты или возврата денег.
2. Требуется независимая проверка правомерности документа/налогов/скидок и ответственного бухгалтера, прежде чем считать сумму официальной проводкой.
3. PostgreSQL содержит сканы с ограничением 2 MiB — это сознательный стартовый вариант. Внешнее S3-хранилище и облако **не обязательны**. При росте объёма понадобится отдельный проверенный путь архива и восстановление файлов, не выходя за границы согласованной инфраструктуры.
4. Не выполняются OCR, парсинг сумм из PDF, автоматическое создание `Payment`, повторный расход или автоматическое признание прибыли.
5. Отдельная проверка физического Android, полный E2E и единый релиз остаются P0.

## Acceptance

- Exact-SHA GitHub CI, изменение 49→50 миграций, прежние SQL hash не изменены, изолированный rollback PASS.
- PostgreSQL E2E загрузка → SHA-256 → чтение файла → привязка к коррекции → отмена, чужая роль 403, неправильный SHA/MIME/повтор 409/422, SQL UPDATE/DELETE отклонены.
- Конкурентные повторные запросы и сверка финансовой сводки OWNER; пустые или отсутствующие файлы блокируют новую корректировку.

**Только после этих проверок допустимо считать технический P0 первичных файлов закрытым.** Полная бухгалтерия и прибыль OWNER остаются NO-GO.
