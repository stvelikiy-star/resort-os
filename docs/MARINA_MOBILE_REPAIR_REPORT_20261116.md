# MARINA SMART — отчёт техника и публикация блюд, 16 ноября 2026

База: PR #522, `86758c54b2e6752fc5c2edb3925e729bf1c3d6c5`. На момент начала этой доработки 34 workflow были успешны, Android preview продолжался. Складской P0 подтверждён PostgreSQL, перезапуском API и настоящим браузерным Staff Web. Это не физическая приёмка телефона.

## Подтверждённое расхождение

Staff Web (`StaffShiftV2`) сдаёт ремонт через POST `/api/v1/ops/tasks/{id}/complete-report`, сохраняет описание работ и запускает серверный переход номера/уборки. Mobile TaskDetail прежде вызывал только PATCH статуса DONE. Ремонт завершался, но мобильного ввода и записи рабочего отчёта не было.

## Что изменено

- TECHNICIAN в карточке ремонта вводит описание (2–2000 символов после удаления краевых пробелов).
- Новый метод существующего StaffApi вызывает тот же серверный complete-report с `summary`, пустыми `checklist` и `evidence_urls`. Новый дублирующий endpoint не создаётся.
- Успех принимается только при совпадающем task_id, статусе DONE, report_recorded=true и допустимом серверном состоянии номера. Успешный отчёт с потерянным последующим GET восстанавливается из подтверждённого ответа и ранее прочитанной задачи, без повторного POST.
- Номер не объявляется готовым после ремонта. DIRTY показывается как передача на уборку, TECH_BLOCK — как продолжающийся ремонт.
- Пустой/пробельный summary сервер отклоняет до БД. Существующие Web-отчёты и отчёты уборки сохраняются.
- Форма пересоздаётся при смене задачи, пользователя, роли или разрешений: текст не переходит на другую работу. Карточка не показывает тип задачи вне рабочего набора роли.
- Неопределённый результат блокирует повторную отправку в текущей форме. После повторного открытия канонический список задач определяет фактический статус; сервер не принимает повторный отчёт завершённой задачи (409).
- Существующий прямой статусный метод остаётся для других разрешённых сценариев. Учебный DEMO обновлён отдельно, без сетевых обращений.

## Проверки и границы

Локально: 459 тестов в 72 наборах Mobile, TypeScript, ESLint, 75/75 закреплённых backend-маршрутов и 7 серверных unit-тестов. API/экранные тесты на DTO, заметку, запрет пустого отчёта, проверку подтверждения, потерю GET после commit, блокировку повторного нажатия и сброс формы при смене задачи. TypeScript/lint и точные backend blob pins проверяются отдельно.

В Kitchen Operations CI добавлен `scripts/verify_mobile_staff_reports_e2e.py` с явным opt-in `ALLOW_STAFF_REPORT_TEST_WRITES=1` и только localhost PostgreSQL/API:

1. Создание сотрудников штатным OWNER API и отдельной синтетической комнаты.
2. Два ремонта одной комнаты: чужой исполнитель 403, пустой отчёт 422, повтор отчёта 409.
3. Первый ремонт завершён, второй остаётся: TECH_BLOCK сохранён, отчёт есть ровно один раз в audit_logs.
4. Последний ремонт завершён: DIRTY и каноническая задача уборки.
5. MAID: неполный чек-лист отклонён, полный передан в IN_INSPECTION; MAID не может принять собственную уборку.
6. OWNER принимает проверку: задача DONE, номер CLEAN, Payment count не меняется.

Этот прогон проверяет сервер с точным мобильным DTO и PostgreSQL. Он не выдаётся за запуск React Native на физическом Android. Браузерный жизненный цикл сотрудников был подтверждён на базе #522; физическая Mobile/Expo Go приёмка остаётся открытой.

## Уточнение матрицы

У OWNER/MANAGER уже есть редактирование/утверждение рецептур и управление закупками; прежнее обозначение всей кухни как read-only было слишком широким. В этой доработке OWNER/MANAGER получили публикацию черновика блюда: явно введённая целая цена 0–100000 сом, все переводы названия и подтверждение. Используется существующий PATCH меню, ответ проверяется, действующее меню/план обновляются. COOK и WAITER не получают управление публикацией; повар сохраняет создание черновиков. Утверждение рецептуры в черновике открыто только OWNER/MANAGER.

Добавлен изолированный PostgreSQL-прогон `verify_mobile_menu_publication_e2e.py`: COOK создаёт черновик, OWNER и MANAGER публикуют, WAITER видит цену, COOK планирует количество порций. Проверяются запреты COOK/WAITER, незаполненный перевод, предел цены и повтор PATCH. Повтор меняет состояние существующего блюда; новую складскую или денежную операцию он не создаёт. CI ещё должен подтвердить этот прогон на новом SHA. Реестр и матрица обновлены без заявления о полном соответствии всех ролей.
