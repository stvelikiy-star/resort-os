# MARINA SMART — восстановление закупок после потери ответа

База: Draft #524, SHA `51a1fd7f9819ddfe287a042a0d65f735ea7efe56`. Ремонт/уборка/приёмка и публикация блюд на базе подтверждены Kitchen Operations PostgreSQL CI. Полный Android/CI базы проверяется отдельно.

## Исправление

В Mobile KitchenProcurement операция REQUEST/RECEIVE ранее хранилась только в React state. После потери ответа и перезапуска её ID исчезал. Теперь полный payload сохраняется до POST в строгом durable storage: SecureStore на native, localStorage с Web Locks в Expo Web. Ошибка записи/чтения не подменяется памятью и блокирует отправку. Данные разделены по отелю и сотруднику, форма пересоздаётся при смене пользователя/роли/прав.

После запуска показываются вид операции, продукт и сохранённое количество. Отправка происходит только после явного повтора. Изменить неизвестную операцию или создать вместо неё новую нельзя. После проверенного ответа с тем же ID и признаком отсутствия платежа запись удаляется. При ошибке очистки тот же payload сохраняется для безопасного повтора. Ошибка следующего GET не превращает подтверждённый POST в повторную запись.

Для нового действия берётся свежий серверный UUID. Снимок списка, оставшийся на экране, не используется повторно. Локальный mutex блокирует двойной тап; Web Locks сериализуют вкладки. Без поддержки Web Locks запись из Expo Web закрыта. Повтор прихода после смены роли на COOK запрещён; журнал при этом не удаляется. Утверждение заявки — замена состояния по постоянному ID, отдельного денежного/складского события не создаёт.

API теперь сериализует одинаковые ID заявки/прихода до блокировок строк. Уникальный конфликт при вставке возвращает 409 и откатывает транзакцию, включая столкновение ID прихода закупки с прямым складским приходом. Старые маршруты, схема БД и финансовые правила сохранены.

## Доказательства

Локально: 470 тестов Mobile в 74 наборах; TypeScript, ESLint, 75 закреплённых backend-маршрутов. Добавлены проверки сохранения до отправки, REQUEST/RECEIVE replay, ошибки хранилища, неверного ack, конкурентного запуска, очистки, повреждённой записи, смены роли и повторного открытия формы.

В Kitchen Operations CI добавлен `verify_procurement_recovery_e2e.py`: восемь одновременных одинаковых заявок/приходов дают одну запись, изменённые данные и одинаковый ID для разных объектов дают 409. Затем настоящий TypeScript-модуль журнала запускается в отдельных Node-процессах с файловым адаптером хранилища: POST против настоящего API коммитится, ответ намеренно теряется; второй процесс читает сохранённый payload и повторяет его. Проверяются одна заявка, одно движение, точный прирост остатка +7 и неизменный Payment count.

Это проверка кода мобильного журнала и PostgreSQL с тестовым адаптером. Она не доказывает работу SecureStore на физическом Android или Expo Go. Реальное устройство, визуальная приёмка и полный общий цикл на едином финальном SHA остаются открыты. Результат нового CI ещё не зафиксирован.
