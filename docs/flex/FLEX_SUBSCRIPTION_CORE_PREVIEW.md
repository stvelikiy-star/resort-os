# MARINA FLEX — безопасное ядро жизненного цикла подписки (preview)

Дата: 2026-11-22. Статус **проект для QA, не живой биллинг**. Относится только к MARINA SMART/FLEX.

## Оплачиваемость и право на доступ

Для любого коммерческого решения необходимы одновременно:
1. Проверенная связка `flex_hotel_links.verified_at` (на основании подписи доверенного MARINA SMART deployment, не поля из запроса).
2. Подписанный действующий коммерческий договор с конкретной гостиницей, сохранённый как immutable `flex_commercial_agreement_versions`.
3. Согласованная валюта KGS, тарифы и срок договора; quote формируется сервером из утверждённого каталога, не из клиентских цен.
4. Для продления после неоплаты — **подтверждённый платёж и нулевой долг по нужному счёту** по отдельному неизменяемому денежному регистру, а не наличие QR, скриншота или статуса, переданного клиентом.

Код `app/flex_subscriptions.py` реализует **только решения о переходах**, а не их исполнение. Аргументы evidence должны в дальнейшем получаться из транзакционно согласованных данных отдельной базы; выставлять `agreement_signed=True` только на основании присланного JSON запрещено.

## Состояния

- `ACTIVE` → `PAYMENT_DUE` только когда пришёл срок и есть подтверждённый неуплаченный остаток.
- `PAYMENT_DUE` → `GRACE` только пока ещё действует предусмотренная договором льгота.
- `PAYMENT_DUE/GRACE` → `SUSPENDED` только после сроков и при сохраняющемся долге.
- `PAYMENT_DUE/GRACE/SUSPENDED` → `ACTIVE` только при оплаченном до нуля счёте с проверяемым идентификатором платежа.
- `GRANDFATHERED` и `CANCELLED` не меняются автоматическими событиями. Сохранение прежних договорных условий обязательно.
- Определение `SUSPENDED` **не вызывает** реальную блокировку гостиницы. Переключение функций требует отдельного проверенного enforcement и перечня безопасных операций.

## Версия договора и черновик

`flex_commercial_agreement_versions`: строго версионированный immutable snapshot, подписавшая сторона, время и digest договора. Подпись и юридическая валидность договора этим SQL **не подтверждаются** — нужны отдельные backend и юридическая приёмка.

`prepare_invoice_preview` возвращает всегда `NON_ISSUABLE`, `invoice_number=None`, `qr_reference=None`. Значение `amount_excluding_unresolved_taxes` — предварительная сумма. Ни один черновик не может использоваться как платёжный или налоговый документ.

`flex_subscription_lifecycle_events`: неизменяемый журнал предполагаемых переходов со ссылками на гостиницу, её подписку, её счёт и проверенный платёж при реактивации. В тестовой схеме не реализована проверка бизнес-переходов на стороне БД, потому что это требует отдельной доверенной транзакционной службы.

## Ограничения

- Не выпускать настоящий инвойс из этого модуля.
- Не генерировать реальный банковский QR или подтверждать платежи.
- Не менять гостиничные `staff_users`, `properties`, PMS брони, кухню, folio и историю.
- Не запускать расписание автоматической блокировки и не продавать незавершённые функции.
- Не применять preview SQL в Production или существующей гостиничной базе.
- Следующий блок — транзакционный ledger/invoice service, проверка платежного провайдера и контроль единицы финансового учёта, затем E2E.

## Acceptance gates

`scripts/marina_flex_subscription_contract_test.py`:
- статус не может измениться до срока или в период неистёкшей льготы;
- нельзя восстановить неоплаченного клиента, принять неподтверждённый платёж, нарушить grandfathered-договор;
- новый черновик всегда НЕ СЧЁТ; одинаковый snapshot даёт один fingerprint.

`scripts/marina_flex_subscription_sql_contract.sql`:
- запрет несогласованных signed contracts, переписывания исторических договоров;
- invoice preview не может иметь статус ISSUED;
- события жизненного цикла не могут ссылаться на чужую гостиницу или неподтверждённую реактивацию;
- финальные события append-only.
