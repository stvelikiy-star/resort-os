# MARINA SMART FLEX P0 — каталог и настройки подписок (без платежей)

**Статус:** код подготовлен в Draft PR #588. Production, PMS main, рабочие отели и денежный учёт не изменяются. Будущая оплата наличными — отдельный этап, здесь не реализуется.

## Что работает после подключения отдельной QA

**SUPER_ADMIN с MFA, по подтверждённой базе ролей:**

1. Просмотр полного коммерческого каталога (включая PLANNED), а не только опубликованных SKU.
2. Создание SKU с постоянным ID, названием и `capability_key` — статус **PLANNED**; новая функция не появляется в работающей PMS и не продаётся автоматически.
3. Добавление **новой неизменяемой** версии KGS цены на дату не ранее чем через 24 часа; старые версии сохраняются; видна история всех версий.
4. Просмотр гостиниц и создание **только конфигурационных черновиков** на основе опубликованных SKU и цен из доверенной базы, не из тела запроса. Указываются название, период и функции.
5. История коммерческих черновиков в карточке гостиницы. Новая запись имеет только `DRAFT`, `OFF`, `KGS`, `subscription_activated=false`, `payments_enabled=false`.

**HOTEL_OWNER:** не может создавать/читать административные черновики. Его действующие подписки, начисления и прочий функционал не изменяются.

### Чем черновик отличается от подписки

**Черновик** — коммерческое предложение и снимок перечня функций/прайс-версий. Он **не** назначает entitlements, не меняет `flex_subscriptions`, не включает ENFORCE, не создаёт договор и счёт, не инициирует приём наличных. Предварительная сумма — описание каталога, **не подтверждение поступления денег**.

Новая PLANNED функция не становится AVAILABLE без отдельного проверенного процесса публикации и карты серверных capabilities. Это сознательный безопасный предел; возможность «активировать всё» не симулируется.

## Изолированное развёртывание QA

Нужна отдельная PostgreSQL 16 **только MARINA FLEX** (не Supabase/PMS public), с применёнными `0001..0010` и дополнительной `0011_flex_catalog_subscription_drafts_preview.sql`. Существующие инструкции по развёртыванию FLEX из `FLEX_ISOLATED_QA_DEPLOYMENT_GATE.md` остаются обязательными.

Создать отдельного пользователя приложения с ограниченными правами и без BYPASSRLS, который состоит в прежних reader-ролях и в `flex_catalog_draft_writer` с **INHERIT FALSE**, а не использовать владельца БД. Сервер `services/api/app/flex_catalog_admin.py` должен работать независимо от существующего PMS API.

FLEX Console BFF требует дополнительно:

```sh
FLEX_ENVIRONMENT=qa
FLEX_ENABLE_QA_CATALOG_DRAFTS=true
FLEX_CATALOG_ADMIN_API_ORIGIN=https://<private-isolated-flex-catalog-api>
```

Эти флаги **дополняют**, а не отменяют `FLEX_OIDC_ISSUER`, `FLEX_API_ORIGIN`, `FLEX_SESSION_KEY`, `FLEX_API_AUDIENCE` и проверенный MFA. Без них формы и административные методы недоступны. Все POST разрешены только по точным путям, с origin/CSRF/session и повторной проверкой роли в Python API.

## Ограниченный API

| Метод | Маршрут | Результат |
|---|---|---|
| GET | `/v1/platform/catalog` | Все SKU, статус, последняя версия цены |
| GET | `/v1/platform/catalog/skus/{sku}/versions` | Неизменяемая история цен |
| POST | `/v1/platform/catalog/skus` | Только PLANNED SKU |
| POST | `/v1/platform/catalog/skus/{sku}/prices` | Только будущая KGS версия |
| GET | `/v1/platform/subscription-drafts[?hotel_id=...]` | История конфигураций |
| POST | `/v1/platform/subscription-drafts` | Только DRAFT/OFF, без side effects |

**Чего нет в этих методах:** регистрации платежа, кассы, онлайн-оплаты, refund, денежного распределения, выставления настоящих счетов, активации и изменения доступа, управления чужими гостиницами через пользовательские поля.
