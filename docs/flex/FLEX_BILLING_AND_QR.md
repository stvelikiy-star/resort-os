# MARINA SMART FLEX 2.0 — биллинг и QR

Только проект. Провайдеры **не подключены и не предполагаются подключёнными**.

## 1. Существующая реализация
Биллинга подписок нет. Есть платежи гостей (`Payment`), идемпотентность платежей гостей, безопасное сравнение вебхук-токенов. Платёжные флаги выключены (fail-closed).

## 2. Три раздельных слоя (обязательно не смешивать)
| Слой | Что делает | Доверие |
|---|---|---|
| A. Счёт | Формирует `flex_invoices` + строки по позициям | Внутренний, детерминированный |
| B. QR / платёжная ссылка | Создаёт платёжное намерение у провайдера, отдаёт QR и ссылку | Внешний, «намерение», **не** подтверждение оплаты |
| C. Подтверждение | Получает от провайдера/банка подтверждение, сверяет, зачисляет | Единственный источник «оплачено» |
Счёт никогда не становится `PAID` по факту показа или сканирования QR, только по подтверждению слоя C (или ручной отметке с документом).

## 3. Провайдеры Кыргызстана (на 22.11.2026, по открытым источникам)
- **ELQR** — единая национальная система QR-платежей: оператор «Элкарт» (с 2020), запуск в мае 2022; к концу 2025 подключены 20 банков и 21 платёжная организация, 100+ приложений ([24.kg](https://24.kg/biznes_info/363651_kak_ELQR_zashest_let_perestroil_platejnyiy_ryinok_kyirgyizstana/)). Стандарт QR и регуляторика — НБКР ([nbkr.kg](https://www.nbkr.kg/DOC/28032025/000000000064177.pdf)).
- Агрегаторы вроде PaymentsGate описывают приём ELQR: сделка `elqr`, сумма 300–150 000 KGS, банки `bakai, mbank, kicb, odengi, demir, megapay`, QR/диплинк, возврат на `successUrl/failUrl` ([документация](https://paymentsgate.readme.io/docs/elqr-in-new)). Webhook/подпись/статусы на изученной странице не раскрыты.
- **Не подтверждено:** условия мерчанта, комиссии, API подтверждения, SLA конкретных банков (MBank, Bakai, KICB, О!Деньги, Оптима, Элсом и др.). Нужны официальные договоры/документация. Ни один провайдер не выбран.
- Вывод: проектировать **адаптер провайдера** (интерфейс), а не конкретную интеграцию; первый этап работает без провайдера (статический QR реквизитов + ручное подтверждение с документом).

## 4. Интерфейс адаптера
```
create_payment_intent(invoice_id, amount, currency, idempotency_key) -> {provider_ref, qr_payload, pay_url, expires_at}
verify_webhook(headers, raw_body) -> bool            # подпись/секрет, окно времени
parse_event(raw_body) -> {provider_ref, status, amount, currency, paid_at, payer_ref}
fetch_status(provider_ref) -> status                 # сверка при пропуске вебхука
refund(provider_ref, amount, idempotency_key)        # если провайдер поддерживает
```

## 5. Расчётный период и жизненный цикл счёта
- `billingAnchorDay` (1–28) на отель; период = [anchor, anchor+1мес). Счёт `DRAFT` за N дней до начала → `ISSUED` → `PARTIALLY_PAID | PAID | OVERDUE | VOID`.
- Счёт содержит строки: SKU, период, qty/использование, цена, скидка, пропорция.
- Кредит-нота = отрицательные строки (возврат, переплата, ошибка). Исходный счёт не изменяется.

## 6. Платежи, переплаты, долги, возвраты
- `flex_payment_events` — сырые события провайдера (неизменяемые, хранятся целиком).
- `flex_payments` — зачисления; **`UNIQUE(provider, providerPaymentId)`** + `UNIQUE(idempotencyKey)` → один платёж не зачтётся дважды.
- `flex_payment_allocations(paymentId, invoiceId, amount)` — распределение частичных/сборных платежей; сумма аллокаций ≤ платежа.
- Переплата → баланс отеля `flex_account_balance` (кредит), зачитывается в следующий счёт; возврат — только отдельной операцией с основанием.
- Долг = ISSUED − Σ allocations (вычисляется, не хранится).

## 7. Идемпотентность и транзакции
Одна транзакция БД: вставка события → проверка уникальности → платёж → аллокации → смена статуса счёта → запись журнала → пересчёт entitlements. Повторный вебхук → тот же результат, без побочных эффектов. Рассинхрон суммы/валюты → событие в `QUARANTINE`, вручную.

## 8. Защита вебхука
Подпись/секрет провайдера, сравнение `hmac.compare_digest`, окно времени (anti-replay), список IP при наличии, лимит запросов, сырой body сохраняется до разбора, ответ 2xx только после фиксации в БД; ошибки не раскрывают детали.

## 9. Напоминания и отправка собственнику
Расписание: за 7/3/1 день до срока и в день срока; каналы — email/WhatsApp (существующие Inbox/WhatsApp-модули, **только если подключены**); счёт PDF + QR; каждое отправление — запись в `flex_notifications` (идемпотентно по счёту+типу).

## 10. Пример (иллюстрация)
Счёт 11 950 KGS. Платёж 5 000 → `PARTIALLY_PAID`, долг 6 950. Платёж 8 000 → аллокация 6 950, остаток 1 050 → кредит отеля. Повтор вебхука на 8 000 с тем же `providerPaymentId` → игнор.

## 11. Риски / приёмка
Риски: нет подтверждённого провайдера; ошибки сверки; пропуск вебхуков (лечится `fetch_status`). Приёмка: дубль вебхука не создаёт второго платежа; частичный/сборный платёж корректен; кредит-нота работает; ни одного перехода в `PAID` без события слоя C; тесты на гонки (параллельные вебхуки).
