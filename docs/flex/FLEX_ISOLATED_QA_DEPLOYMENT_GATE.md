# MARINA SMART FLEX — изолированная QA-среда: эксплуатационный допуск

**Дата:** 2026-11-22. **Статус:** план реального развёртывания, ещё не выполнен. Всё относится только к MARINA SMART/FLEX. Дизайн делает Claude Code. KÖL, гостиничные базы и Production не изменяются.

## 1. Что подтверждено

- Интеграционный кандидат #585 поверх #574–584: 10 preview SQL-слоёв на **отдельной одноразовой PostgreSQL 16**, чистая установка, `pg_dump` → восстановление во вторую БД, повторная проверка RLS и финансовых инвариантов — PASS.
- Новый `scripts/marina_flex_qa_db_preflight.sql` отказывает, если имя БД не `flex_ci`, версия не PostgreSQL 16, обнаружена Supabase/PMS или база не пуста.
- `scripts/marina_flex_restore_acceptance.sql` подтверждает отсутствие PUBLIC EXECUTE на всех `flex_*` функциях и отсутствие INSERT/UPDATE/DELETE у reader-ролей — проверяется также после восстановления.
- Эти тесты **не подтверждают** защищённое внешнее хранение копий, Production-готовность, реальные банки, TLS из Интернета или живой сервис.

## 2. Инфраструктура: утверждён GitHub + Vercel + Cloudflare

**GitHub:** хранение кода и отдельная ветка FLEX, проверка на одном SHA.
**Vercel:** отдельный проект MARINA FLEX QA с закрытыми Preview интерфейсом и API.
**Cloudflare:** DNS, HTTPS, ограничение доступа к QA, защита и R2 для
зашифрованных резервных копий; не менять действующий MARINA SMART домен.

Для новой базы **не** переиспользовать гостиничную PostgreSQL или чужие
проекты. Предпочтительный путь управления ресурсами — выделенная
PostgreSQL 16 через **Vercel Marketplace storage integration** после
проверки доступных провайдеров, цены, `CREATE ROLE`/`NOINHERIT`,
транзакций, RLS и корректности подключения из Vercel Functions.
Подключение внешней Postgres-интеграции через Vercel не означает,
что Vercel сам является базой данных.

**Текущие SQL 0001–0011 — автономный PostgreSQL 16 preview:**
требуют ограничения публичной схемы, прав исполнителя, аудита SECURITY
DEFINER и проверки миграций до установки в постоянную QA. Для managed
Postgres нужно убедиться, что нет открытого Data API и имеется независимый
restore. Cloudflare D1 (SQLite) не поддерживает эту схему как есть.

**Railway в проекте не используется и исключён из плана.**
Любая реальная Vercel storage интеграция с ненулевой стоимостью требует
отдельного подтверждения до создания.

## 3. Обязательные границы безопасности

- Отдельные JWT issuer/audience + EdDSA public keys, короткий срок токена, MFA и проверка platform memberships в базе. Нет общей гостиничной учётки OWNER вместо SUPER_ADMIN.
- Только серверное использование `FLEX_DATABASE_URL`, отличный от `DATABASE_URL` гостиничной PMS. Никогда не передавать его веб-клиенту, не использовать service_role key на фронтенде.
- Start with only `app.flex_control_plane` (read-only) behind private QA ingress. `app.flex_onboarding`, `app.flex_partner_portal` и подписывающий PMS-agent подключать только после дополнительной проверки доверенных ключей и владения объектом.
- Не использовать `app.flex_qa_settlement` для внешних webhook. `FLEX_SETTLEMENT_MODE=CI_DISPOSABLE_ONLY` допускается только внутри GitHub Actions, **не** в постоянной QA и тем более Production.
- Финансы, выставление реальных счетов, реальные QR, банк, продление и ограничения гостиниц — выключены до подписанного провайдера и отдельной приёмки. В гостиничной PMS никакого автоматического ENFORCE.
- Строго ограничить source IP → DB, TLS, секреты в окружении провайдера, аудит и алерты; не записывать приватные ключи, DB-пароли или webhooks в GitHub.

## 4. Контрольный порядок

1. Подготовить отдельный Vercel FLEX QA и выбрать совместимую PostgreSQL-интеграцию через Vercel. Утвердить стоимость, регион и лимит расходов.
2. Проверить закрытую схему FLEX и преобразовать 11 preview миграций в контролируемые versioned migrations без CI-фикстур.
3. Настроить отдельный зашифрованный off-site backup в Cloudflare R2, независимое восстановление, TTL и документированный RPO/RTO.
4. Выпустить restricted runtime DB user и проверить отсутствие `BYPASSRLS`, `INHERIT`, прав DDL, прямых пользовательских подключений. Прогнать отрицательный доступ Hotel A→Hotel B.
5. Подготовить Vercel Preview и защищённый Cloudflare DNS/TLS/Access адрес QA только для тестировщиков; проверить health, JWT, MFA и RLS через HTTP.
6. Внести 2 синтетические гостиницы и договорные черновики без платёжных операций, выполнить полный нефинансовый E2E.
7. Проверить, что существующий `app.ms.go.kg` и MARINA SMART Cloudflare DNS/Vercel маршруты не меняются при подключении отдельного FLEX QA.
8. После устранения Release RC Truth через официальный процесс нового коммерческого релиза — формальная приёмка `GO/NO-GO`.

## 5. Независимые причины NO-GO

- Не утверждена площадка или расходы на новый QA проект.
- Не проверена совместимость автономных PostgreSQL ролей и миграций с выбранной интеграцией базы через Vercel.
- Нет отдельного issuer и защищённой DB runtime identity.
- Нет внешнего зашифрованного backup/restore для постоянной среды.
- Нет реального банковского sandbox/settlement — он не должен быть эмулирован на Production.
- Исторический November Release RC Truth намеренно не принимает новые FLEX-файлы в старый релиз.
- Не подтверждена реальная связка `MARINA SMART ↔ MARINA FLEX` и визуальная приёмка Claude Code.

Нельзя объявлять Production GO по одному успешному CI. Выплаты агентам/инвесторам остаются отложенными.
