# MARINA FLEX — INVESTOR PORTAL (архитектура и интерфейсы)

> **Сверка с Codex (22.11.2026):** роли платформы в реализации: SUPER_ADMIN, BILLING, HOTEL_OWNER, SALES_AGENT, INVESTOR; INVESTOR_MANAGER отложена; выплаты отложены. См. `FLEX_RECONCILIATION_CODEX.md`.

Только проект. Production, действующие финансовые операции, БД, авторизация и тарифы не менялись. Дополняет FLEX 1 и FLEX 2.0; формулы и учёт — в `FLEX_INVESTOR_FINANCE.md`.

## 1. Существующая реализация
Роли `StaffRole`: OWNER, MANAGER и др. — роли **отеля**; роли INVESTOR нет. Платформенного контура и биллинга подписок нет (см. FLEX 2.0). Есть `AuditLog`, права по секциям, `owner_*` (аналитика отеля, **к инвестору не относится и не раскрывается**).

## 2. Архитектурные границы (обязательные)
| Контур | Кто | Что видит | Деньги |
|---|---|---|---|
| Отель (staff, OWNER) | персонал отеля | свой отель | платит подписку MARINA |
| Агент MARINA (`flex_agents`) | продавцы | свои отели и комиссии | комиссии `flex_commission_*` |
| **Инвестор (`flex_investors`)** | вкладчики в MARINA | свой договор и разрешённая агрегированная статистика | выплаты `flex_inv_*` |
| Платформа (`flex_platform_users`) | Super Admin и др. | всё | — |
Три денежных потока **не смешиваются**: таблицы, API-пути, роли и регистры раздельны. Комиссия агента не уменьшает базу инвестора автоматически и наоборот — только по договору (см. FINANCE §3, решение владельца). Нельзя использовать `BookingAgent`, `staff_users`, `StaffRole`.

## 3. Роль INVESTOR
Отдельная таблица пользователей `flex_investor_users`, отдельный вход и сессии, 2FA обязательна, журнал входов. Токен несёт `investorId`; никакого `propertyId` и `tenantId` отелей.

Видит: свои договоры, свои начисления/выплаты/документы, агрегированную статистику платформы **в разрешённом договором объёме** (например, общий MRR без разбивки по отелям — только если владелец включил для договора `statsScope`).
Не видит: данные гостей, брони, финансы и названия отдельных отелей, тарифы и цены каталога, агентов и комиссии, других инвесторов, их суммы и условия, общий список обязательств компании.

## 4. RBAC
| Действие | INVESTOR | SUPER_ADMIN | INVESTOR_MANAGER* | BILLING | AUDITOR |
|---|---|---|---|---|---|
| Свои договоры/начисления/выплаты (чтение) | ✔ | ✔ | ✔ | — | ✔ |
| Создать/изменить договор | — | ✔ | ✔ (черновик) | — | — |
| Утвердить договор | — | ✔ | — | — | — |
| Провести выплату | — | ✔ | ✔ (по лимиту) | — | — |
| Корректировка/сторно | — | ✔ (двойное подтверждение) | — | — | — |
| Просмотр обязательств компании | — | ✔ | ✔ | ✔ | ✔ |
| Правка тарифов/каталога | — | ✔ | — | ✔ | — |
*Новая роль платформы `INVESTOR_MANAGER`, вводится по решению владельца. Утверждение договоров и выплат — принцип «четырёх глаз».

## 5. RLS
- Все `flex_inv_*` таблицы имеют `investorId`; включён RLS: `investorId = current_setting('flex.investor_id')::uuid`. Контекст ставится из токена в начале транзакции; без контекста — 0 строк (fail-closed).
- Платформенные роли — отдельные политики; агенты и отели не имеют **никаких** GRANT на `flex_inv_*`.
- Статистика инвестору — только через материализованные представления `flex_inv_public_stats` (агрегаты без `propertyId`), не из регистров отелей.
- Подавление малых групп: агрегаты по < N отелей не публикуются (не раскрывают конкретный отель).

## 6. Модель данных (кратко; полная — в FINANCE §6)
`flex_investors`, `flex_investor_users`, `flex_inv_contracts`, `flex_inv_contract_versions`, `flex_inv_accruals`, `flex_inv_payouts`, `flex_inv_payout_lines`, `flex_inv_adjustments`, `flex_inv_documents`, `flex_inv_notifications`, `flex_inv_period_close`, `flex_inv_public_stats` (view).

## 7. API
Инвестор (`/api/v1/investor/*`, только свои данные):
```
GET /me                          GET /contracts            GET /contracts/{id}
GET /earnings?from=&to=&group=day|week|month|year|all
GET /accruals?status=ACCRUED|AVAILABLE|PAID
GET /payouts                     GET /documents            GET /documents/{id}/download
GET /forecast?horizon=            GET /stats/platform       (в рамках statsScope)
GET /notifications  POST /notifications/{id}/read
```
Платформа (`/api/v1/flex/investors/*`): CRUD инвесторов; `POST /contracts` (черновик) → `POST /contracts/{id}/approve`; `POST /accruals/run?period=`; `POST /payouts` (`Idempotency-Key`); `POST /adjustments`; `GET /obligations`; `GET /audit`. Все — роль, транзакция, журнал, идемпотентность.

## 9. Уведомления
События: начислено, стало доступным, выплата проведена, корректировка, смена фазы, документ добавлен. Каналы email/WhatsApp **только если подключены**; запись `flex_inv_notifications` идемпотентна по (событие, объект).

## 10. Тестовые сценарии
1. Инвестор A запрашивает договор/начисление B по ID → 404 (не 403), в журнале попытка.
2. Прямой SQL под ролью инвестора без `flex.investor_id` → 0 строк.
3. Агент и сотрудник отеля получают отказ на `/investor/*` и на `flex_inv_*`.
4. `/stats/platform` не содержит `propertyId`, названий отелей и групп < N.
5. Повторный запуск начисления за период → без дублей.
6. Параллельные выплаты на один остаток → вторая отклоняется (блокировка + CHECK).
7. Возврат платежа отеля → отрицательное начисление, статусы пересчитаны.
8. Смена фазы ровно в момент достижения возврата вклада (граница) — сумма сверх возврата корректно делится.
9. Договор не утверждён → начисления не создаются.
10. Суммарные обязательства превышают лимит → договор не утверждается.
11. Выплата без второго подтверждения → отказ.
12. Скачивание чужого документа → 404.

## 11. Риски / приёмка
Риски: утечка финансов отелей и чужих условий; смешение с агентскими комиссиями; двойная выплата; ошибочная база расчёта; **юридическая квалификация договоров** (долевое участие в выручке, регулирование, налоги, лицензирование) — только юрист. Приёмка: изоляция по RLS и API подтверждена тестами 1–12; три денежных контура не имеют общих таблиц и ролей; все суммы воспроизводимы из первичных регистров.
