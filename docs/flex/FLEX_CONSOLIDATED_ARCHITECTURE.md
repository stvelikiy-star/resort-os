## 2. Архитектурное решение — централизованный коммерческий control plane

```text
                          MARINA FLEX CONTROL PLANE
                отдельная защищённая БД и PLATFORM API
      hotel_registry / feature_catalog / subscriptions / invoices
      verified_payment_events / payment_allocations / commissions
            investor_contracts / payouts / platform_audit
                      |                      |
              authenticated service    authenticated service
                      |                      |
      MARINA SMART HOTEL A            MARINA SMART HOTEL B
      отдельная БД / API              отдельная БД / API
                     \                /
                FUTURE SHARED-TENANT MARINA
                 (только после отдельной QA)
```

**Инвариант:** центральная база FLEX не владеет персональными данными гостей, гостиничными бронями, folio или внутренними платежами гостя. Она владеет только коммерческим договором между MARINA и гостиницей и агрегированными безопасными техническими показателями.

Отдельный `flex_hotel_id` (UUID) служит идентификатором договора. Таблица соответствия `flex_hotel_links` сопоставляет его с проверенным `deployment_id`, `property_id`, `tenant_id` (опционально), используя **серверную регистрацию**. Нельзя принимать `hotel_id` из URL, JWT гостя или присланного HTTP-заголовка как доверенный идентификатор.

Изолированные гостиничные экземпляры получают подписанные, короткоживущие контексты возможностей только от доверенного control plane, через узконаправленный служебный канал. Провал связи не должен внезапно закрывать размещение действующих гостей; запасное поведение и TTL утверждаются отдельно.

## 3. Монетизация: catalog -> price-version -> subscription-item -> entitlement

- **Feature/SKU** — отдельная продаваемая функция, а не физическая кнопка. `capability_key` — неизменяемый машинный ключ; одна операция может зависеть от нескольких SKU.
- **Catalog** — доступность продукта: `AVAILABLE` / `BETA` / `PLANNED`. Планируемое нельзя продавать как готовое.
- **Plan / bundle** — набор SKU. База 10 000 KGS — целевой **новый** тариф (не навязывается существующим договорам).
- **Price version** — неизменяемый снимок цены, валюты, периода, скидки, периода действия и договорных условий.
- **Subscription item** — функция определённого отеля с началом/концом, источником (покупка/пакет/пробный/грант), согласованной ценой, статусом.
- **Entitlement** — серверный результат: действие, объект, гостиница, период, работник и технический capability. Работает поверх существующих RBAC, а не вместо них.

Коммерческие ограничения: `OFF` -> `SHADOW` -> `ENFORCE`; переключатель по конкретному отелю. **По умолчанию OFF для всех текущих гостиниц**. До подтверждённой миграции выдаются grandfathered договоры с сохранением текущего доступа.

`services/api/app/flex_foundation.py` — только чистые функции расчёта, не подключён к маршрутам. Поддерживает `OFF/SHADOW/ENFORCE`, `ON/GRACE/READ_ONLY/OFF`, нерушимое ядро и безопасные операции. Включать `ENFORCE` до готовности SKU-карты и E2E запрещено.

## 4. Финансовый учёт: единый источник подтверждённых денег

```text
Invoice -> immutable invoice lines -> payment intent -> provider event
       -> verified payment (or two-person manual confirmation)
       -> allocation(invoice_line_id, payment_id, amount)
       -> [commission entries] + [investor accrual entries] + dashboards
```

- `invoice_lines` хранят SKU, версию цены, количество, налог, скидку и итог **на момент выставления**.
- Подтверждённое поступление денег отделено от статуса счёта и факта показа QR. QR/чек/скриншот не являются банковским подтверждением.
- `payment_event` — неизменяемое входящее событие с уникальным `provider,event_id`; результат применения — отдельная запись `processing_attempt`, не UPDATE исходного события.
- `allocations` связаны с конкретной строкой счёта; сумма распределений не больше подтверждённого платежа, остаток = кредит отеля. Сверка под блокировками БД.
- `agent_commissions` и `investor_accruals` — **раздельные** регистры обязательств, не платежи из банка.
- Возврат = отдельная корректировка и сторно, с явной ссылкой на исходную запись, без переписывания истории.
- Суммы — `numeric(18,2)` в БД, `Decimal` в Python, валюта обязательна. `MRR`, `invoiced`, `cash_received`, `accrued`, `paid_out` не смешивать.

Текущая чистая реализация `allocate_confirmed_payment` намеренно **не** делает денежную операцию: она рассчитывает детерминированный план аллокаций для будущей транзакции; проверка подписи, валюты, idempotency-key, `SELECT ... FOR UPDATE` и фиксация платежа обязательны в инфраструктурном слое.

## 5. QR, биллинг и блокировка

Счета: `DRAFT` -> `ISSUED` -> `PARTIALLY_PAID` / `PAID` / `VOID` по правилам неизменяемых записей.
Подписка: `TRIAL` / `ACTIVE` -> `PAYMENT_DUE` -> `GRACE` -> `SUSPENDED` -> `REACTIVATED` или `CANCELLED`.
Не делать глобальную блокировку таблицы `properties` или отзыв доступа сотрудников. Ограничения должны быть **на уровне разрешённых новых операций**, при этом доступны получение счёта, оплата, безопасное завершение текущего проживания, возврат, аудит и выгрузка данных. Длительность grace согласуется договором.

До договора с реальным платёжным провайдером:
1. `payment_intent` может создаваться только в тестовом адаптере;
2. QR обозначается TEST/DEMO, не как реальный платёж;
3. ручное подтверждение требует разделения ролей и следа в аудите;
4. реального автоматического `PAID` нет.

## 6. Агенты

Торговый `SALES_AGENT` не равен гостиничному `StaffRole.AGENT`. Обязательны: идентификатор привлечения, продажи SKU, история атрибуции, версия комиссионных правил, разовые и повторные комиссии по договору, статус начислено/к выплате/выплачено/сторно. Основа — **конкретная подтверждённая аллокация**, не включённый UI-переключатель.

## 7. Инвесторы

Персональный `INVESTOR` видит свои договоры и данные: начислено за день/неделю/месяц, подтверждено к выплате, фактически выплачено, вернувшаяся часть вложений и остаток. Договор имеет версионированные параметры: scope гостиниц, база распределения, доля, бонусный срок, ограничение выплат. Старые и новые коммерческие презентации **не подменяют утверждённый договор**.

**Обязательное исправление к FLEX_INVESTOR_FINANCE:** явно разделять `recognized_repayment` по начислениям и `cash_repaid` по фактическим выплатам; не переводить инвестора в следующую фазу по недоказанному поступлению денег. Метод перехода между фазами и возвраты утверждает владелец и юрист.

Контроль суммарных обязательств учитывает пересекающиеся scope; один и тот же рубль/сом не должен считаться дважды в выручке.

## 10. Решения перед включением следующих фаз

1. База действующих договоров и миграция на новые тарифы: только explicit consent.
2. Договорная ставка и состав базы агента и инвестора (налоги/комиссии/возвраты).
3. По какому событию инвестиционный взнос считается возвращённым: accrual vs actual payouts.
4. Приоритет блокировок, grace и отдельные безопасные операции.
5. Подтверждённый способ QR через конкретного provider и коммерческий договор с ним.
6. Ограничение суммы совокупных обязательств компании.
7. Модель центрального API: отдельная защищённая БД, политика связи с каждым инстансом.
8. Метод mid-month prorate: в коде пока только **вариант календарных дней, не утверждённый тариф**.

## 11. Quality gates

- Полный green contract CI этой ветки.
- Фаза DB: пустая установка + независимое восстановление + негативные межотельные тесты.
- Фаза платежей: повторный webhook, refund, partial, overpayment, 2 concurrent callbacks, expiry.
- Фаза агента: продажа SKU, продление, комиссионное сторно, приватность.
- Фаза инвестора: closed periods, cap, repayment by paid amounts, payout dual approval, investor isolation.
- Фаза ENFORCE: сначала пилот 1 гостиницы, rollback флагом, сохранность всех активных броней.
