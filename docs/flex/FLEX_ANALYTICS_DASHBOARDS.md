# MARINA SMART FLEX 2.0 — аналитика и дашборды

Только проект. Источник всех метрик — события и регистры FLEX; в существующие аналитические модули `owner_*` (аналитика отеля) FLEX не вмешивается.

## 1. Три регистра выручки (чтобы не было двойного учёта)
| Регистр | Что | Источник | Когда признаётся |
|---|---|---|---|
| Подписочная (MRR/ARR, «контрактная») | Нормализованная месячная стоимость действующих позиций | `flex_subscription_items` | пока позиция активна |
| Начисленная (accrued) | Суммы выставленных счетов за период | `flex_invoice_lines` | на дату периода счёта |
| Полученная (cash) | Подтверждённые аллокации платежей | `flex_payment_allocations` | на дату подтверждения |
Каждая сумма попадает в каждый регистр **один раз**; кредит-ноты входят со знаком «−» в тот же регистр и период.

## 2. Метрики и формулы
- MRR = Σ нормализованных месячных цен активных позиций (сезонные — делить на месяцы сезона). ARR = MRR×12.
- ARPU = MRR / число платящих отелей. LTV = ARPU × средний срок жизни (или ARPU / churn, если churn > 0 и история достаточна; **иначе не показывать**).
- Churn (клиентов) = отключённые за период / активные на начало. Revenue churn — по MRR.
- Активные / заблокированные отели — по состоянию на дату (`flex_subscription_state_history`).
- Новые подключения, отключения за день — `flex_change_log` по типам событий.
- Выручка по модулю/функции — по строкам счетов и аллокациям.
- Топ/редко используемые — продажи (позиции) и **использование** (`flex_usage_events`: свойство, функция, количество, время; пишется сервером при вызове платной функции).
- Доход по агенту, комиссии начисленные/утверждённые/выплаченные — `flex_commission_entries`, `flex_agent_payouts`.
- Дебиторка = ISSUED − Σ аллокаций, по возрастам (0–30, 31–60, 61+).
- Продления/неоплаты — доля счетов `PAID` в срок.
- Сезонная выручка — группировка по `season` позиции.
- Прогноз поступлений = выставленные открытые счета × историческая доля оплаты в срок + ожидаемые счета по активным подпискам. Метка «прогноз», показывается отдельно от факта.
- Когорты: когорта = месяц первого `ACTIVE`; удержание = доля когорты с активной подпиской через n месяцев (по MRR и по числу).

## 3. События (append-only, `flex_events`)
`subscription.created|changed|cancelled`, `item.connected|disconnected|limit_exceeded`, `invoice.issued|voided`, `payment.confirmed|refunded`, `state.changed`, `usage.recorded`, `commission.accrued|reversed|paid`. Поля: id, ts, propertyId, agentId?, actor, payload.

## 4. Хранение и производительность
Источник правды — транзакционные таблицы; дашборды читают **агрегаты**: `flex_metrics_daily(day, dim_*, metric, value)`, пересчитываются идемпотентным заданием (можно пересчитать день заново). Фильтры: день/месяц/год, отель, агент, модуль, тариф. Права: Super Admin — всё; агент — только свои срезы; отель — только своё.

## 5. Интерфейс (Future Luxury 2.0, Desktop + Mobile, RU/KG/EN, Dark/Light)
Верх: период + фильтры. Ряд плиток: MRR, ARR, ARPU, активные/заблокированные, отток, дебиторка. Далее: график MRR/accrued/cash (три линии), воронка подключений, таблица модулей/функций (продажи+использование), агенты (доход/комиссии/выплаты), когортная матрица, прогноз с пометкой. Mobile: плитки в столбец, графики с переключателем периода, таблицы → карточки.

## 6. Риски / приёмка
Двойной учёт (закрывается регистрами), неправильные формулы LTV, нагрузка. Приёмка: сверка Σcash = Σаллокаций; MRR воспроизводим из позиций; пересчёт дня идемпотентен; агент не видит чужих данных; фильтры дают согласованные суммы.
