# MARINA FLEX — безопасная регистрация коммерческой гостиницы

Дата: 2026-11-22. **Статус: изолированный QA-прототип, НЕ Production**.

## Сценарий, который уже покрывает код

1. Доверенный issuer выдаёт подписанный EdDSA JWT с MFA для платформенного `SUPER_ADMIN`.
2. Сервис MARINA FLEX проверяет подпись и роль в БД, а не из присланного поля JSON/JWT.
3. `POST /v1/onboarding/hotels` принимает название и KGS, обязательный `Idempotency-Key`.
4. Под отдельным DB `flex_onboarding_writer` (NOLOGIN, не наследуемый) выполняется транзакция: lock по `subject_id+idempotency_key`, проверка повторного запроса, создание `flex_hotels(status=PENDING)`, запись `flex_hotel_onboarding_requests`, неизменяемый `flex_audit_events`.
5. Идентичный повтор отвечает `200` с тем же UUID; отличающийся payload при том же ключе — `409`. Новый запрос — `201`.
6. Созданный клиент появляется только в коммерческом реестре MARINA FLEX; **PMS БД, hotel setup, staff, гостевые данные, модульные права, подписки и платежи не затронуты**.

Неизвестным актёрам, гостиничным OWNER, агентам и инвесторам запрещена регистрация. Роль владельца гостиницы сама по себе не даёт управлять сетью.

## Чего нет

Это **не** активация гостиницы, не подтверждение владения PMS, не self-service onboarding. Поле `flex_hotel_links.verified_at` не устанавливается: пока нет отдельной проверяемой криптографической attestation от доверенного PMS deployment. Нельзя создавать связь отеля по заявленному `property_id` из клиентского тела.

Для полного онбординга требуются отдельно:
- реестр доверенных deployment public keys + безопасная enrollment-процедура;
- одноразовый challenge с TTL и проверка signed PMS attestation;
- сверка tenant/property context и tenant isolation в QA;
- административное подтверждение договорных условий и статуса коммерческого клиента;
- tenant-scoped service-to-service entitlements, подписанный снимок прав;
- резервная копия и проверка восстановления отдельной центральной FLEX БД.

## Риски и инварианты

- Действующий гостиничный `main` и DB не изменяются. SQL `0004_flex_hotel_onboarding_preview.sql` выполняется **только в одноразовой QA**.
- Привилегии writer: INSERT гостиницы только с `PENDING`, запись своего idempotency и аудита. Нет UPDATE/DELETE, счетов, платежей, блокировки.
- Токены и админские роли внешнего провайдера ещё не интегрированы в реальную инфраструктуру. Приватные ключи не хранятся в репозитории.
- CI: signed HTTP, доступы и отсутствие привилегий; сценарии реальной регистрации позже требуют отдельной настройки среды и обзора безопасности.
- Вся коммерческая функциональность до оплаты и согласованной миграции **OFF** для текущих отелей.
